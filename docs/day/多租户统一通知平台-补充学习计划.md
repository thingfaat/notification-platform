# “多租户统一通知平台”补充学习计划

> 适用背景：`notification-platform` 是“30 天高级 Java 后端自研转岗冲刺计划”中的第一个自研项目，目前已在约 Day 14 提前完成；`short_link` 是本次要拆解学习的知识星球后端项目，现成的 `short_link_frontend` 只用于接口联调和效果验证，不纳入学习计划。本计划不重做短链基础功能，而是把知识星球后端项目中真正有增量价值的部分，转化为通知平台的 Day 15—Day 30 补充训练。

## 一、结论先行

知识星球短链项目值得学习，但应该“学习问题与取舍，重新实现关键实验”，不应直接复制代码。

当前通知平台已经完成了：

- Maven 多模块与领域分层；
- 多租户字段、SQL 租户拦截、TenantContext 在 HTTP/MQ/线程池间传递；
- 通知任务、消息状态机、模板渲染；
- RocketMQ、Outbox、消费幂等、失败重试和死信；
- Redis 令牌桶、每日配额；
- 多供应商路由、线程池隔离、超时、熔断和故障切换；
- 短码、重定向、本地缓存 + Redis、负缓存、Bloom 防穿透；
- 点击事件异步统计、PV/UV；
- Prometheus 指标和首轮 k6 压测。

因此，知识星球项目中的 CRUD、Base62、普通重定向、基础缓存、普通 Bloom、基础 Prometheus 和单页表单都不是主学习目标。

后半程最值得投入的是：

1. 分布式 ID 与短码生成的正确性实验；
2. Redis Cluster 槽位、Hash Tag 与批处理；
3. 可过期 Bloom、重建期间可信状态和故障降级；
4. RocketMQ 集群消费、广播消费、重试、死信与 Rebalance；
5. 分库分表路由均衡性与 ShardingSphere 小规模实证；
6. 在线扩容中的双写、回填、对账、切流和回滚；
7. 容量规划、故障注入、告警闭环；
8. 把通知平台目前的认证、定时发送、批量发送和真实渠道补成工程闭环。

## 二、知识星球项目中值得学习的内容

### 1. 短码生成不是“Base62 编码”这么简单

值得学习：

- 随机短码、哈希短码、数据库 ID、Snowflake ID 再 Base62 的差异；
- 码空间大小、生日碰撞概率、可枚举性和租户维度；
- 机器 ID 分配、时钟回拨、同毫秒序列耗尽；
- “生成器尽量唯一”与“数据库唯一约束最终兜底”的边界。

学习方式：保留通知平台现有随机短码为默认实现，新增一个可替换的 Snowflake/Base62 实验实现；注入可控制时钟，做并发、回拨和序列耗尽测试，最后写一份选型 ADR，不凭感觉替换线上策略。

特别注意：知识星球实现把 Snowflake ID 对码空间取模，这会重新引入碰撞，不能把“Snowflake 唯一”直接等同于“取模后的短码唯一”。

### 2. 创建短链的并发幂等与业务语义

值得学习：缓存预检、细粒度分布式锁、锁内二次检查、数据库唯一约束、冲突重试。

但通知平台不能直接照搬“相同原始 URL 永远复用同一短码”。通知场景往往需要按租户、活动、消息甚至接收人跟踪点击；过度复用会让归因失真。

学习方式：先明确幂等键：

- 管理型短链可用 `tenant + application + requestId`；
- 营销追踪短链可用 `tenant + messageId + targetUrl`；
- 数据库唯一约束负责正确性；
- 分布式锁只负责减少冲突和无效写，不承担最终正确性。

### 3. Redis Cluster 的键模型

值得学习：CRC16 槽位、Hash Tag、MOVED/ASK、拓扑刷新、同槽批处理、热 Key、Big Key、节点故障时的降级策略。

学习方式：搭建最小 Redis Cluster；为同一短码的映射、计数、负缓存设计 Hash Tag；编写槽位测试和批量按槽分组实验，比较逐条访问、错误跨槽批处理与同槽批处理的耗时和错误表现。

### 4. Bloom Filter 的完整生命周期

通知平台现在已有 Bloom 重建可信标记和 fail-open，这是很好的基础。知识星球项目新增的价值是时间分片思想：让有过期时间的数据可以随着时间窗口自然退出，避免一个永久 Bitmap 越来越大、误判率持续上升。

学习方式：实现“小规模可验证版”，不照搬 2.16 亿/时间片的配置。先根据真实样本量计算位数、哈希函数和理论误判率，再验证：

- 当前片写入与历史片查询；
- 时间片轮换和过期清理；
- 启动预热；
- 重建时 fail-open；
- Redis 故障时不误伤合法短链；
- 实测误判率是否接近理论值。

### 5. 明确排除：Redis Stream 不纳入必做范围

知识星球项目用 Redis Stream 同步各实例的本地 Bloom 和本地缓存，但通知平台已经使用 RocketMQ，因此 Redis Stream 的实现、测试、部署和运维均不纳入必做范围。下面内容只作为可选的反例阅读，不占用学习日，也不作为验收条件或面试准备要求。

源码审查需要掌握以下问题：

- 同一个消费组是负载均衡，不是广播；改成“每节点一个消费组”后，又会产生消费组生命周期和离线组清理问题；
- 创建消费组时没有可靠地确保 Stream 已存在，异常却统一记录为“消费组已存在”，可能掩盖初始化失败；
- 发布节点没有直接更新本地 Bloom，而消费者又跳过来源于自身节点的消息，导致发布节点本地 Bloom 漏更新；
- 消费只读取 `lastConsumed`，没有处理或接管 PEL 中未确认的历史消息；
- 处理失败后没有完整的重试、毒消息隔离和死信策略；
- 发布异常被吞掉，只记录日志，缓存一致性只能依赖 TTL 或其他修复机制；
- Stream 裁剪、离线消费者和未确认消息之间缺少明确的数据保留契约。

通知平台已有 RocketMQ，本计划不实现 Redis Stream。短链映射尽量保持不可变；确需同步本地缓存失效时，优先复用 RocketMQ，并以版本号、短 TTL 或定时校准作为最终一致性兜底。时间不足时可以完全跳过本小节。

### 6. 分库分表最重要的是“路由正确且均匀”

知识星球项目中“库索引和表索引取模相关，导致每个库只命中少数表”的问题非常值得学习。这比记住 ShardingSphere 配置语法更有价值。

学习方式：先做纯 Java 路由模拟器，对 100 万个短码统计各库、各表分布和变异系数；再搭 2 库 × 4 表的 ShardingSphere PoC。需要理解：

- 分片键选择和租户倾斜；
- 库表算法相关性；
- 跨分片分页、聚合和排序成本；
- 全局唯一 ID；
- 广播表、绑定表；
- 什么数据量与写入压力下才值得真正拆分。

不建议直接在通知平台创建 32 库 × 256 表。当前实测端到端稳定吞吐受 5 token/s 渠道限流约束，远未到必须大规模分片的阶段。

### 7. 在线扩容与数据迁移

这是知识星球项目中面试价值最高、但现有代码完成度不足的部分。其迁移、双写和扩容监控类目前基本处于整文件注释状态，因此应把它当需求说明，而不是完成实现。

学习方式：在小规模分片 PoC 上完整走一次：

1. 新旧路由版本化；
2. 新数据可靠双写，失败进入补偿表或 Outbox；
3. 历史数据使用主键游标分批回填，不用大 OFFSET；
4. 数量、分桶 checksum、抽样字段三级对账；
5. 读新失败时读旧并 read-repair；
6. 灰度切读；
7. 停止旧写；
8. 保留回滚窗口后再下线旧结构。

### 8. 可观测性、容量和高可用

值得学习：缓存命中率、Bloom 拦截率、RocketMQ 消费积压与重试/死信、分片倾斜、迁移积压、Outbox backlog、渠道 P95/P99、熔断状态和告警恢复。

学习方式：不要写“100 万 QPS”作为项目结论，除非真正测到。先定义 SLO，再做热点命中、冷数据回源、非法短码、Redis 故障、MQ 故障、渠道慢调用等场景，给出首个饱和点、恢复时间和容量余量。

## 三、不应照搬的内容

- 不把文档中的“100 万 QPS”当实测结果；
- 不直接上 32 库 × 256 表；
- 不复制 Snowflake ID 取模后仍宣称全局唯一；
- 不把整文件注释的双写/迁移代码当成已完成能力；
- 不把 Redis Stream 同组消费误认为广播；
- 不在已经使用 RocketMQ 的通知平台中再引入 Redis Stream 充当第二套 Broker；
- 不在配置文件中提交真实 IP、账号、Redis/MySQL/Nacos 密码；
- 不照搬不匹配的 Spring Cloud/Alibaba 版本与旧 Fastjson 依赖；
- 不用大量 MockMvc 循环代替真实网络压测和集成测试；
- 不为展示技术栈而同时保留重复的缓存、Bloom、DAO 和数据源实现。

## 四、Day 15—Day 30 补充计划

建议每天 4—6 小时。每天必须产出：一个可运行增量、一组自动化验证、一段原理总结、至少一个可面试问题。若当天只能投入 2 小时，就把该 Day 拆成两个自然日，不压缩验收。

### Day 15：知识星球短链项目反向工程

目标：建立自己的理解，不从代码复制开始。

动手任务：画出创建、跳转、缓存读写、Bloom 判断、分片路由和扩容六条链路；整理通知平台已有能力、重复能力、增量能力和问题代码。Redis Stream 同步链路不属于本日必做内容。

验收：不用看代码讲清一次创建与跳转；能指出至少 5 个设计风险，并解释为什么通知场景不能按原 URL 全局复用短码。

面试输出：`短链系统的读写路径为什么要分开设计？`

### Day 16：短码生成与分布式 ID 实验

目标：掌握随机码、哈希、Snowflake + Base62 的选择依据。

动手任务：为通知平台抽象两种生成策略；使用可注入 Clock；测试 100 万次生成、32 线程并发、5 ms/50 ms/严重回拨和序列耗尽；计算 8 位、10 位 Base62 碰撞概率。

验收：生产默认策略不盲目替换；测试无重复或所有冲突均被唯一约束和重试正确处理；形成一份短码选型 ADR。

面试输出：`Snowflake 转 Base62 后为什么仍可能重复？`

### Day 17：通知短链的幂等与并发正确性

目标：把知识星球的“锁 + 双检 + 唯一约束”转为符合通知业务的模型。

动手任务：定义管理短链和消息追踪短链的不同幂等键；实现数据库唯一约束兜底；增加同 requestId 并发、短码冲突和事务回滚集成测试；按需要增加细粒度分布式锁。

验收：50—100 个并发请求下没有重复业务记录；锁失效或 Redis 不可用时正确性仍由数据库保证。

面试输出：`分布式锁和唯一索引各负责什么？`

### Day 18：Redis Cluster 与槽位实验

目标：从“会用 Redis”升级到理解集群键模型。

动手任务：搭最小 Redis Cluster；实现 CRC16 槽位计算验证；为短链映射、计数和负缓存设计 Hash Tag；完成批量按槽分组；观察节点故障、MOVED/ASK 和拓扑刷新。

验收：给定任意一组 Key 能判断是否同槽；跨槽批处理问题有可复现测试；节点切换后系统能恢复且降级行为明确。

面试输出：`Redis Cluster 为什么需要 Hash Tag？`

### Day 19：时间分片 Bloom Filter

目标：解决带有效期短链的 Bloom 删除和误判率增长问题。

动手任务：根据样本量计算参数；仅实现共享 Redis 时间分片，不增加依赖广播同步的本地 Bloom；完成当前片、历史片、轮换、清理和启动预热；保留现有 ready/trusted 状态和 fail-open；采集理论与实际误判率。整个实现不使用 Redis Stream。

验收：重建或 Redis 故障期间合法短链不被误伤；过期片可清理；误判率有数据而非口头描述。

面试输出：`Bloom Filter 为什么不能简单删除，时间分片解决了什么？`

### Day 20：RocketMQ 消息模型与可靠性实战

目标：基于项目现有 RocketMQ，真正理解集群消费、广播消费、重复投递、Rebalance、重试和死信，而不是再引入 Redis Stream。

动手任务：启动两个 Worker 实例；验证同一消费组下每条通知只由一个实例处理；观察实例上下线时的 Rebalance；注入消费超时、进程退出、重复消息和毒消息；验证重试次数、退避、幂等和死信处理。额外用一个低风险事件比较 RocketMQ 广播消费与集群消费，但缓存正确性必须由版本号、短 TTL 或定时校准兜底。

验收：业务发送消息在两实例间只处理一次业务结果；消费者在处理完成前退出后消息能够重新投递；重复投递不重复调用渠道；毒消息最终进入死信并可人工恢复；能说明广播模式为什么不适合承担必须可靠重试的核心业务消息。

面试输出：`RocketMQ 集群消费与广播消费有什么区别，重复消费如何处理？`

### Day 21：动态限流与降级策略

目标：把固定配置升级为按租户、应用、渠道动态治理。

动手任务：比较现有自研令牌桶/熔断器与 Sentinel 的边界；选择配置中心或数据库配置实现规则热更新；支持版本号、校验、回滚和旧 Key 平滑过期。

验收：运行中修改单租户速率无需重启；错误配置不会击穿全部租户；关键规则变更有审计记录。

面试输出：`限流规则动态更新时如何避免新旧规则互相污染？`

### Day 22：分片路由数学与容量阈值

目标：先证明需要分片，再选择分片方式。

动手任务：按通知任务、消息明细、发送记录、短链点击分别估算日增量和保留期；编写 100 万 Key 路由模拟器；复现库表取模相关导致的倾斜，再用独立位段或独立哈希修正。

验收：输出数据增长表、单表阈值、分片键选择和分布统计；能解释为什么当前项目暂不需要 32 × 256。

面试输出：`分库和分表为什么不能随便对同一个 hash 取模？`

### Day 23：ShardingSphere 必做实战

目标：掌握真实路由行为和常见面试问题，而不是只会写 YAML 或背概念。

动手任务：搭建 2 库 × 4 表的可运行环境；选择一个高增长附属表做实战；配置标准分片策略和分布式主键；验证单键路由、范围查询、分页、聚合、事务、广播表、绑定表和全局 ID；分别观察命中单分片与广播路由时生成的真实 SQL。

验收：SQL 日志可证明路由结果；自动化测试覆盖增删改查和租户隔离；至少复现一个跨分片分页/聚合问题以及一个路由配置错误；能独立解释分片键、分片算法、广播表、绑定表、全局 ID、跨库事务和扩容难点。

面试输出：`ShardingSphere 帮你透明了什么，又没有透明什么？`

### Day 24：在线扩容（一）——双写与回填

目标：把知识星球中注释状态的迁移设想做成可运行实验。

动手任务：新旧路由版本化；新写通过 Outbox 或补偿表可靠同步；回填使用主键游标、checkpoint、限速和幂等 upsert；进程重启后可续跑。

验收：人为制造新分片写失败后能够补偿；回填中断重启不重头开始、不漏数据；不使用大 OFFSET。

面试输出：`在线迁移为什么不能只做异步双写？`

### Day 25：在线扩容（二）——对账、切流与回滚

目标：完成迁移闭环。

动手任务：实现数量、分桶 checksum、抽样字段对账；读新失败读旧并 read-repair；通过开关进行灰度切读、停止旧写和回滚；记录迁移 lag 与失败数。

验收：随机注入 1% 丢写能够被对账发现并修复；切流失败可回滚；形成迁移 Runbook。

面试输出：`双写迁移如何证明没有丢数据？`

### Day 26：容量、故障注入与告警闭环

目标：把高可用从“有组件”变成“有证据”。

动手任务：补齐 Grafana/Alertmanager；增加 Bloom 信任状态、RocketMQ 消费积压/重试/死信、分片倾斜、迁移 lag、Outbox backlog、渠道耗时与熔断指标；注入 Redis、RocketMQ、MySQL 和渠道慢调用故障。

验收：每种故障都有预期降级、告警和恢复记录；告警恢复后能自动 resolved；报告写首个饱和点和恢复时间，不写未经验证的百万 QPS。

面试输出：`Redis 挂了以后哪些功能应 fail-open，哪些应 fail-closed？`

### Day 27：真实租户认证与越权测试

目标：补上通知平台当前最明显的生产缺口。

动手任务：管理端使用 JWT，业务应用调用使用 AK/SK 或 HMAC 签名；加入 timestamp、nonce 和重放保护；tenantId 从认证主体生成，不再信任任意 `X-Tenant-Id`；限制 Actuator 暴露。

验收：伪造 tenant header 无法越权；跨租户 CRUD、MQ、缓存、短链和线程池上下文均有自动化测试；过期签名和重复 nonce 被拒绝。

面试输出：`共享 Schema 的多租户系统如何做纵深隔离？`

### Day 28：批量、定时与取消语义

目标：补齐已有字段但尚未完整执行的业务能力。

动手任务：让 `scheduleTime` 真正控制入队时间；大批量接收人分块落库，避免一个超大事务；定义 CREATED/QUEUED 阶段的取消边界；重复 requestId 返回原结果而非笼统报错。

验收：定时任务不会提前发送；万级接收人不会形成不可控大事务；并发取消与入队状态转换有测试；同 requestId 可安全重试。

面试输出：`批量任务为什么不应在一个事务里逐条插入全部消息？`

### Day 29：真实渠道与送达回执

目标：从 Mock Sender 走向最小真实闭环。

动手任务：接入 MailHog/SMTP 作为真实邮件渠道；保存 providerMessageId；实现签名回调、回调幂等、乱序回调处理；完成 SENT → DELIVERED/DELIVERY_FAILED 状态流转；敏感配置改用环境变量或 secret。

验收：真实邮件可查看；重复、乱序和伪造回调都有测试；收件人和密钥不出现在普通日志与仓库配置中。

面试输出：`第三方回调重复、乱序、延迟时如何保证状态正确？`

### Day 30：全链路验收、接口资产与面试沉淀

目标：把补充学习转成可演示、可复述的项目能力。

动手任务：修复 k6 中 19 位 ID 被 JavaScript Number 截断的问题；跑创建、定时、发送、回执、短链、点击、人工重试和故障恢复全链路；完善 OpenAPI 文档、IDE HTTP/Postman 请求集合和一键回归脚本；更新 README、架构图、压测报告和迁移 Runbook。`short_link_frontend` 只用于验证知识星球短链接口，不开发新的前端页面。

验收：一个命令启动环境；只使用请求集合或回归脚本即可在 5 分钟内完成后端全链路演示；所有核心测试通过；能脱稿讲 10 个项目问题，并明确哪些数字是实测、哪些是容量估算。

面试输出：准备以下三段叙事：

1. 一个一致性问题：Outbox/消费幂等/回调乱序；
2. 一个性能问题：限流饱和、缓存或分片倾斜；
3. 一个可用性问题：Redis/MQ/渠道故障与恢复。
