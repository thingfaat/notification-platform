## 6. 首个饱和点

- 首先达到上限的资源：通知渠道令牌桶，补充速率为 5 token/s。
- 出现饱和时的 RPS：任务创建 10 RPS；5 RPS 未出现持续积压。
- 对应 P95/P99：24.25 ms / 39.87 ms（HTTP 创建接口）。
- 对应错误率：HTTP 0%，业务 0%。
- 证据：10 RPS 压测结束 15 秒后仍有 519 条消息未终态、501 条 Outbox 未完成；Worker 日志明确出现 `TOKEN_BUCKET_EXHAUSTED`。停止施压后，积压最迟在复查点 +3 分 05 秒全部收敛。
- 为什么判断它是瓶颈，而不是相关现象：10 RPS 高于配置的 5 token/s 持续补充速率；同时 CPU 峰值仅 4.17%、Hikari Pending 为 0、渠道执行器 Queue 为 0、拒绝次数为 0，排除了 CPU、数据库连接池和渠道线程池先饱和的可能。

## 7. 优化实验

- 原始假设：本地验收工具持续采集每个短链请求的 INFO 日志，会让终端输出反压应用，造成与真实业务容量无关的尾部超时。
- 本次只修改的一个变量：仅把 Server 的 `TraceIdFilter` 日志级别从 INFO 临时调为 WARN；业务代码、缓存与压测参数不变。
- 修改前结果：50 RPS 共 6000 次，5 次网络超时；错误率 0.0833%，k6 汇总实际速率 45.919 RPS，P95 8.97 ms，最大 138.60 ms。由于 5 个请求进入 graceful stop，汇总时长被拉长。
- 修改后结果：50 RPS 共 6001 次，错误率 0%，实际速率 50.004 RPS，P95 9.68 ms，P99 14.50 ms，最大 78.35 ms。
- 是否验证假设：是。异常来自本地日志采集链路，不是短链业务资源饱和；正式结果采用修改后的测试口径。
- 是否产生新的瓶颈：没有。200 RPS 下 CPU、Heap、Hikari Pending、错误率和 dropped iterations 均无饱和信号。

## 8. 容量结论

- 当前单实例稳定 RPS：短链热点跳转至少 200 RPS；本轮未继续提高压力，因此不能把 200 RPS 当作容量上限。
- 通知任务创建接口容量：至少 10 RPS，且 HTTP SLO 全部通过；但若要求下游不持续积压，当前单租户/应用在该限流配置下的稳定端到端吞吐为 5 RPS。
- 容量结论对应的 SLO：短链错误率 < 1%、P95 < 200 ms、P99 < 500 ms；任务创建错误率 < 1%、P95 < 500 ms、P99 < 1000 ms，且 Outbox 最终收敛到 0。
- 推荐日常流量：短链暂按 140 RPS；需要近实时送达的通知暂按 3.5 RPS。两者均按已验证稳定值预留 30% 余量。
- 建议预留比例：至少 30%；正式生产环境仍需在独立压测机、接近生产的数据规模和网络条件下重新标定。
- 超过容量后的保护方式：入口限流/租户配额、Outbox 削峰、延迟重试、线程池隔离与拒绝指标、熔断和安全渠道切换，并对 `QUEUED`、`THROTTLED`、Outbox NEW、MQ Diff 设置告警。
- 下一步优化方向：先修复 k6 脚本的雪花 ID 精度问题；为 Outbox backlog、消息状态和 RocketMQ Diff 增加可回溯指标；若业务要稳定超过 5 RPS，再评估提高令牌补充速率、按租户/应用拆桶或横向扩展渠道供应商，而不是先扩大线程池。
